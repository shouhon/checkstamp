# checkstamp 要件定義書

- 文書版: 1.2
- 状態: 初版・実装済み（現在のCLI版と確認範囲は[開発計画](development-plan.md)を参照）
- 目的: 検証コマンドの結果を、実行時に指定したファイルの状態と結び付けて保存する。

## 1. 利用場面と完成条件

テストや静的検査の成功後にコードを追加修正した場合、以前の結果が現在も対応しているか確認するために使う。実行結果と対象のハッシュを保存し、後から対象が変わったことを検出できることを完成条件とする。

確認の範囲は、利用者が明示した入力と記録できた実行条件に限る。依存ファイルを自動で推定せず、未指定の設定、環境変数、外部サービスの変化まで検証済みとは扱わない。

## 2. 初版の対象

- Windows 11・PowerShellで利用する、非対話型のCLIとする。
- 任意の作業ディレクトリで動作させ、Gitへの依存は必須にしない。
- 実行ファイルへの引数を配列として渡し、CLIが勝手にシェル用の文字列へ組み立て直さない。
- 初版で直接起動するのは通常の実行ファイルとする。PowerShellスクリプトなどは、呼び出し側が明示的に pwsh -NoProfile -File などを指定する。
- テストの選択、依存関係の自動解析、結果のキャッシュによる実行省略、自動再検証、CI連携、電子署名は初版に含めない。

## 3. コマンド

| コマンド | 要件 |
|---|---|
| checkstamp run --label <名前> --input <対象> [--input <対象> ...] [--json または --json-summary] -- <コマンド> [引数...] | 入力を記録し、コマンドを実行して結果を保存する。 |
| checkstamp status <実行ID> [--json または --json-summary] | 保存済みの結果と現在の入力を照合する。検証コマンドは再実行しない。 |
| checkstamp --help / --version | 日本語の使い方、有効性の範囲、版番号を表示する。 |

使用例は、checkstamp run --label unit --input src --input tests --input package.json --input bun.lock -- bun test とする。この例の入力が実際のプロジェクトに存在することは実行前に確認する。

--input は1つ以上必要とし、ファイルまたはディレクトリを実行時の作業ディレクトリから指定する。存在しない入力、作業ディレクトリの外へ出る指定、初版で扱えない入力は、子プロセスの起動前にエラーにする。

入力収集の失敗は、元の指定順での番号（1始まり）と、確認できた原因区分を標準エラーおよび両JSONモードの issues に同じ説明で示す。正規化・重複除去・並べ替えの前の番号を保持し、不存在・読取不能・未対応の種類や名前・不正な範囲・管理領域を区別する。番号や詳細な原因を特定できなければ推測しない。診断は最初に検出した1件とし、入力名、絶対パス、ファイル本文、環境変数、子の引数、OSエラー全文を転記しない。既存の終了コード・機械判定用コード・未取得の値を維持する。

## 4. 入力と実行結果の記録

- ディレクトリ指定では、隠しファイルを含む配下の通常ファイルを対象にする。.git の管理領域と .checkstamp は除外し、除外した範囲を記録する。
- 初版では入力木に含まれるシンボリックリンクや特殊ファイルを未対応として報告し、参照先へ暗黙に移動しない。見つかった場合は実行前の収集を失敗させる。
- 実行前後に、対象の一覧・相対パス・種類・SHA-256を記録する。追加・削除・内容変更のいずれかがあれば、入力が変わった結果として扱う。
- 実行開始時と終了時の内容が同じでも、途中で変更されて元に戻された操作までは検出を保証しない。
- 子プロセスの作業ディレクトリと、引き継ぐ環境を勝手に変えない。ツールの動作に不要な引数追加、コマンドの置き換え、暗黙のシェル起動をしない。
- 子プロセスの終了コード、開始・終了のUTC日時、作業ディレクトリ、実行ファイルの解決先、引数列のSHA-256、入力範囲、checkstampの版を保存する。
- 引数列のハッシュは引数の境界を保った形式から計算する。引数の生値、環境変数の値、標準出力・標準エラーの本文、入力ファイルの本文は保存しない。
- 実行条件の記録は再実行コマンドの復元を保証するものではない。機密値を保存しないために省略した情報と、未確認の外部条件を結果に明記する。

状態は実行開始時の作業ディレクトリの .checkstamp/runs/<実行ID>.json に保存する。実行IDは同時実行でも衝突しないものとし、同名のラベルでも過去の記録を上書きしない。status は同じ作業ディレクトリから実行する。

実行前に記録先への保存が可能か確認する。開始済み・完了済みの状態は途中の書き込みで壊れないよう保存する。正常終了が記録されていない結果を、検証成功と推定しない。

.checkstamp が別用途で使われている場合は停止する。.gitignore やプロジェクト設定を変更せず、必要な除外方法をヘルプで案内する。

## 5. 判定と出力

| status の値 | 意味 |
|---|---|
| valid | 子プロセスが0で終了し、実行前後と現在の入力が一致し、記録の読取も完了した。 |
| stale | 記録は成立しているが、現在の入力が記録後に変わっている。 |
| failed | 子プロセスが0以外で終了した。 |
| unstable | 子プロセスは終了したが、実行前後で入力が異なる。 |
| interrupted | 中断を受けた事実をツールが記録した。 |
| unknown | 記録が未完了・破損・未対応、または現在の入力を十分に読めない。 |
| invalid_arguments | 引数の誤り。 |

複数の事実が併存する場合は issues と入力の差分に残す。status の優先順位は unknown、interrupted、failed、unstable、stale、valid とする。valid は指定した入力の範囲に対応する判定であり、プロジェクト全体の正しさや環境全体の同一性を保証しない。

入力の削除は内容の変化として扱い、存在や内容を調べる権限がない場合の unknown と区別する。

通常の run では子プロセスの標準出力・標準エラーを元の出力先へ流し、ツール自身の実行IDや診断は標準エラーに出す。run --json と run --json-summary では子プロセスの両出力を標準エラーへ流し、標準出力を結果JSONオブジェクト1件に保つ。これらのモードでは子プロセスの2つの出力元の区別と相互の順序は保証しない。

--json の詳細出力には schema_version、tool、command、run_id、label、status、child_exit_code、実行日時、記録した実行条件、coverage、入力の差分、issues を含める。issues は機械判定用の code と日本語の説明を持つ。保存先の記録と結果JSONで判定を食い違わせない。

--json-summary は schema_version、command、run_id、status、child_exit_code、change_count、current_change_count、issues のみを返し、入力一覧や差分の明細を出さない。実行前後の変更件数を change_count、最後の記録から現在の変更件数を current_change_count とし、変更されたファイル・ディレクトリのパスを各1件として数える。未確認の件数と未取得の終了コードは0と推定せず null とする。run の current_change_count は常に null とする。実行前後の詳細な一覧と差分は保存記録に残し、現在の一覧と差分は status --json で取得する。--json と --json-summary の併用・重複は引数エラーとする。判定・終了コード・issues の意味はどちらのJSONモードでも維持する。

## 6. 終了コードと中断

run と status は終了コードの意味を分ける。

| コマンド | 終了コードの要件 |
|---|---|
| run: 子プロセスを起動できた場合 | 元の終了コードをそのまま返し、child_exit_code にも保存する。 |
| run: 起動前の記録失敗・起動不能 | 125。引数の誤りは64。子プロセスは起動しない。 |
| status: valid | 0。 |
| status: stale / failed / unstable / interrupted | 1。 |
| status: unknown | 2。 |
| status: 引数の誤り | 64。 |

子プロセスの起動後に保存や入力の再読取が失敗した場合も、元の終了コードは変えずに返す。記録の不成立は標準エラーと、出力可能な結果JSONで明示する。run の終了コード0だけで記録成立とは判断せず、status で確認する設計とする。

中断時は子プロセスへ中断を伝え、管理できる子プロセスを意図せず残さない。子プロセスの終了コードを取得できればその値を返し、取得できない場合は125とし、成功の記録を作らない。ツールの強制終了で未完了の記録が残った場合、status は unknown とする。

## 7. 受入条件

1. 元のコマンドへ引数の境界、作業ディレクトリ、必要な環境を保って渡す。空白、日本語、引用符を含む引数を試験する。
2. 子プロセスの終了コードを、0・1・2・64・125などでも元の値のまま返す。
3. 実行後の入力変更で stale となり、再確認なしに valid を返さない。
4. 実行中に生じ、終了時にも残った入力の追加・削除・変更は unstable とする。
5. 読取失敗、未対応の入力、記録破損、未知の保存形式、未完了の記録を成功扱いにしない。
6. 中断と同時実行を扱い、実行IDや保存ファイルが衝突しない。
7. 通常表示と両JSONモードで標準出力の契約を守り、出力量に比例して無制限にメモリーへ蓄積しない。要約は入力や差分の件数に比例して大きくならず、詳細記録と判定・終了コード・問題が一致する。
8. 機密値を含む引数や出力を、ツールの記録や独自のエラーメッセージへ転記しない。
9. status は子プロセスや検査を再実行せず、対象ファイルを変更しない。

実装時は、終了コードや出力量、中断、入力の書換えを制御できる検証用プログラムで確認する。実際の認証情報は検証に使わない。

## 8. 版管理と実装時に決める事項

本書の初版は1.0とする。実装開始時の初回CLI版は0.1.0、保存・JSON形式は schema_version: 1 とし、版番号の正本を1か所に定めて --version と配布物を一致させる。現在のCLI版と検証結果は開発計画へ記載する。

実装言語はGoとする。ソースはGitHub、実行ファイルはGitHub Releasesで配布し、ScoopまたはZIPの手動展開で導入する。ライセンスはMITとし、配布の詳細は[リリース手順](releasing.md)を参照する。Windowsでのプロセス管理方式は[実装文書](input-and-record.md#実行と中断)に記載する。初版では他の3つのCLIを必須依存にしない。検証結果の有効範囲を広げる変更では、何を追加で記録・照合するかを本書へ反映する。
